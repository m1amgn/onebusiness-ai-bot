## 1. Problem

The application runs today only as development processes beside a shared PostgreSQL and Redis. `docker compose up --build` starts two services, `postgres` and `redis` (EXECUTED `docker compose config --services` at `c09d2fc`). The assignment asks for one Compose command that runs the web frontend, the API, PostgreSQL, Redis and the workers (R10, R11), and a README that explains setup and assumptions. The owner added on 2026-10-27 (section 19): the stack is built as close to a production server as possible, a document says what a server still needs, and the owner tests the finished Docker build in person, with no development-server run.

What exists and what S8 changes (the designer's exploration notes A, B, C; key files read by the designer):

- Every port in the bot, worker and API composition roots already has its real adapter: umbrella section 14 L1 is complete at `c09d2fc`. The remaining non-real adapters are the user-selectable `fake` transcriber and the designed `Unconfigured*`/`Unavailable*` degradations. S8 changes no composition root. S8 runs the workers on Linux prefork for the first time (`backend/AGENTS.md:405`).
- The PostgreSQL budget of L3 holds: 5 (api, one uvicorn process) + 5 (bot) + 5 (transcribe, one child) + 10 (notify, two children) = 25 of the 97 non-superuser slots; the worker main processes and beat open no engine. Redis clients have no cap in code; S8 measures them.
- L4 is partly done: the 15 s broken-worker wait is already 120 s (`c28204c`). Still fixed-time: `scripts/whisper.test.mjs:77` (2 s start-up poll), `backend/tests/integration/test_worker_runtime.py:38,73` (8 s, 12 s), `backend/tests/integration/test_worker_schedule.py:27,31,33,41` (8 s, `sleep(2)` standing in for "the worker holds the ETA message", 15 s, 18 s); outside L4's list, the same class: `scripts/dev-proxy.test.mjs:60` (a 1 s race).
- The upstream whisper.cpp image: `ghcr.io/ggml-org/whisper.cpp:main` is linux/amd64 only and `main-arm64` is linux/arm64 (EXECUTED `docker manifest inspect`, 2026-10-27); it runs as root from `bash -c`, ships ffmpeg and curl, keeps `download-ggml-model.sh` at `/app/models/` (not on `PATH`), has only the English `base.en` model built in, writes `--convert`'s temporary WAV to `--tmp-dir` (default `.`, i.e. `/app`), answers `GET /health` with 200 once the model is loaded (the port refuses connections while it loads), and answers a failed conversion with 500 `{"error":"FFmpeg conversion failed."}`, which S5's mapping matches (W3 holds).
- The API serves `GET /health` without the `/api` prefix (`backend/src/taskbot/entrypoints/api/app.py:72`); every other route is under `/api`.

Designer decisions that the code answers:

- **Provider default.** `.env.example` and the settings default (`infrastructure/settings/transcription.py:7`) carry `TRANSCRIPTION_PROVIDER=openai`, because D-09 makes `openai` the Compose stack's provider and a keyless voice message must get the `provider_unavailable` reply. Today both say `whisper_server` and `backend/tests/unit/test_env_example.py` pins the example to the default, so a copied `.env` would send voice to a whisper server that is not running and fail after five retries with `transient_exhausted`. Two tests assert the old default and change with it: `backend/tests/unit/test_bot_settings.py:13` and `backend/tests/unit/test_transcription_factory.py:175`. A developer's own `.env` sets `whisper_server`; `docs/development.md` says so.
- **Whisper image per machine.** `docker/whisper.Dockerfile` has two index-digest-pinned base stages, `main` (amd64) and `main-arm64` (arm64), and selects one with BuildKit's `TARGETARCH`; it adds a non-root user that owns `/models`.
- **Signing in without a token.** A `seed` service in the profile `tools` runs `python -m taskbot.entrypoints.seed` with the database, Redis and `WEB_BASE_URL` of the stack: `docker compose run --rm seed <telegram_user_id> "<text>"` creates a task and prints a dashboard link on port 8080. A reviewer without a Telegram token signs in with it; the acceptance script creates its rows with it.

"Every service healthy" (umbrella 3.1) stays: seven services `healthy` and `migrate` `exited (0)`, plus `whisper` `healthy` in the profile run. `depends_on` with `required: false` needs Compose 2.20 or later; the README names that minimum. With the `whisper` profile on, `worker-transcribe` therefore waits for the model download, and no voice job can race it.

**Model download.** `docker/whisper.Dockerfile` adds a script that does nothing when `/models/ggml-<model>.bin` exists; otherwise it downloads with `curl -fL --retry 5` into `ggml-<model>.bin.part`, checks the SHA-256 that the script pins for the supported models (`base` at least; an unknown model name stops with a message naming `WHISPER_MODEL`), and renames the file. An interrupted download leaves only a `.part` file, which the next start replaces.

**Environment.** Application services get their variables through `environment:` with Compose interpolation from `.env`, never `env_file:`, because `.env` also carries development values (`localhost` URLs, the Vite port) that must not reach a container. Compose sets these itself: `DATABASE_URL` = `postgresql+asyncpg://${POSTGRES_USER:-taskbot}:${POSTGRES_PASSWORD:-taskbot}@postgres:5432/${POSTGRES_DB:-taskbot}` (the settings model refuses another scheme), `REDIS_URL` = `redis://redis:6379/0`, `WHISPER_SERVER_URL` = `http://whisper:8080`, `WEB_BASE_URL` = `http://localhost:${WEB_PORT:-8080}`. Each service receives only what its settings model reads (exploration B 3.2): `api` the two URLs and `LOG_LEVEL`; `bot` adds the token, `WEB_BASE_URL`, the extractor settings, `TRANSCRIPTION_PROVIDER` and `OPENAI_API_KEY` (for `/start`); `worker-transcribe` the token, the provider and extractor settings; `worker-notify` the token; `migrate` `DATABASE_URL`; `seed` the URLs, `WEB_BASE_URL` and the extractor settings. The worker health check needs `REDIS_URL` in the container environment: the Celery app reads `BrokerSettings` at import, whose default is `localhost`.

**Shared hardening** (S8-D2 b, c). Extension fields `x-hardening` (`read_only: true`, `security_opt: [no-new-privileges:true]`, `cap_drop: [ALL]`) and `x-logging` (`json-file`, `max-size: 10m`, `max-file: "3"`) are merged into every service. YAML merge is shallow, so each service lists its own complete `tmpfs`: `/tmp` for the backend services (it holds the notify beat schedule directory `taskbot-<uid>`, which therefore starts empty at each container start, harmless for a 60 s schedule); `/var/run/postgresql:uid=70,gid=70,mode=1777` and `/tmp` for `postgres`; `/tmp` for `web` (`nginx-unprivileged` keeps its pid and temp paths there) and for `whisper` (`--tmp-dir /tmp`). `postgres` and `redis` run with an explicit `user:` so their entrypoints skip the root-to-user switch that needs `SETUID`/`SETGID`; the shared volumes were created by these images with the same owners (70 and 999). Memory limits use one form, `mem_limit`, set from the peak `memory.peak` of each container's cgroup over the acceptance run and one full `yarn verify` for the shared `postgres` and `redis` (they serve every worktree's tests), with a margin of at least 2×; the `whisper` limit is `${WHISPER_MEM_LIMIT:-<measured for base>}`, and the README gives the value per model. A service that cannot run under one of these rules says why in a comment beside it.

**Pinned images** (S8-D2 a). Every `FROM` (uv included, as a pinned `FROM … AS uv` stage instead of `COPY --from=<image>`) and every pulled `image:` names a patch-level tag and its multi-platform index digest, resolved at implementation and recorded in the implementation note with `docker buildx imagetools inspect` showing amd64 and arm64.

### 3.3 The web image and nginx

Build stage on `node:26-alpine`: `npm install --global yarn@1.22.22` (Node 26 images bundle no Yarn; "never npm install" in `AGENTS.md` governs project packages), copy the root `package.json`, `frontend/package.json` and `yarn.lock`, `yarn install --frozen-lockfile` (development dependencies included: the build needs `vite` and `typescript`), then copy `frontend/` and run `yarn workspace frontend build`. The generated API client is committed, so the build does not regenerate it. `docker/web.Dockerfile.dockerignore` repeats the root exclusions (`**/node_modules`, `.git`, `.tasks`, `.agent-collab`, `**/.env*` except the example, `backend`, `frontend/dist`, `*.tsbuildinfo`) and keeps `frontend/`. Runtime on `nginxinc/nginx-unprivileged` (alpine, uid 101, port 8080), with `docker/nginx.conf` installed as `/etc/nginx/conf.d/default.conf` (the image's `nginx.conf` keeps `pid` and temp paths in `/tmp`) and `docker/nginx-headers.conf` beside it.

`docker/nginx.conf`, one `server` on 8080, `server_tokens off`:

- `resolver 127.0.0.11 valid=10s ipv6=off;` and in each `/api` location `set $api_upstream api:8000; proxy_pass http://$api_upstream;` (no URI part, so `/api/...?…` reaches the API unchanged), so a recreated `api` container is found and `web` starts even when `api` is down.
- `location /api/events`: `proxy_http_version 1.1`, `proxy_set_header Connection ""`, `proxy_buffering off`, `proxy_cache off`, `proxy_read_timeout 1h` (above the 15 s keep-alive, Z4). When the API ends or drops the stream, nginx ends the browser's response; the dashboard's `onerror` then closes the source, takes a new ticket and reconnects with back-off of at most 30 s (`frontend/src/…/eventStream.ts`).
- `location /api/`: `client_max_body_size 64k` (the only bodies are a status change and an empty ticket request).
- Both `/api` locations set `Host`, `X-Real-IP`, `X-Forwarded-For` and `X-Forwarded-Proto $scheme`; `docs/deployment.md` shows the TLS proxy in front and the `real_ip` lines it adds. `access_log` uses a format that writes `$uri`, not `$request`, so the one-time SSE ticket in the query string is not logged.
- `location = /index.html` with `Cache-Control: no-cache`; `location /assets/` with `try_files $uri =404` and `Cache-Control: public, max-age=31536000, immutable`; `location /` with `try_files $uri /index.html`; `location = /favicon.ico { return 204; }`.
- `gzip on; gzip_types text/css application/javascript application/json image/svg+xml;` (`text/html` is always compressed; `text/event-stream` is not listed, so the stream is never buffered for compression).
- Every location that sets a header includes `nginx-headers.conf`, because nginx inherits `add_header` only into a level that sets none. The file holds, each with `always`: `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; font-src 'self'; connect-src 'self'; img-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'self'` (the built page has no inline script or style, fonts are bundled files, the stream is same-origin); `X-Content-Type-Options: nosniff`; `X-Frame-Options: DENY`; `Referrer-Policy: no-referrer` (the token travels in the URL fragment, which the dashboard removes at once); `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`.

### 3.6 The end-to-end test (S8-D8)

`backend/tests/integration/test_end_to_end.py` composes existing harnesses on one R-ISO database and one Redis namespace: `configure_bot` and `BotSession` (`tests/bot_runtime.py`; the namespace is the one `configure_bot` takes, `harness.settings.redis_namespace`, never a second `child()`), `running_worker("transcribe")` and `running_worker("notify")` with `HOOKS` and `TASKBOT_TEST_S5_RECEIPTS` set (real Celery processes, the fake transcriber, the recording notifier and the fixture voice source), and the API in-process through `open_api_services` and `api_server` on port 0. One bot run, `bot_cli.run` as a task, fed in stages (the session re-reads its updates on each poll):

1. `/dashboard`; read the link from the recorded `sendMessage`; take a ticket with the bearer and open `/api/events`; read `: connected`.
2. A text update and a voice update.
3. Assert: the text reply; `task.created` for both tasks on the stream; the voice job `done` with provider `fake`; the recorded notification `Task created: [demo transcript] … (demo mode)`; `GET /api/tasks` with the bearer returns both tasks with their `source_text`.
4. Stop the bot with `session.control.signal()`.

The test asserts events and states, never elapsed time; its deadlines are the shared cold-start budget (`tests/processes.py:9`).

### 3.7 L4: waits on readiness

- `scripts/whisper.test.mjs`: the start-up and signal polls wait for the fake server's marker files up to one 30 s deadline instead of 2 s; the `spawnSync` and test timeouts rise to match.
- `test_worker_runtime.py:38,73`: the waits read log records that appear as soon as the event happens; only their deadlines move to the shared cold-start budget. Line 38 waits for a soft-limit effect, not readiness, and stays an effect wait.
- `test_worker_schedule.py`: `sleep(2)` becomes a poll of `inspect().scheduled()` on the worker's node until the countdown task appears, then SIGTERM; lines 27, 33 and 41 take the shared budget.
- `scripts/dev-proxy.test.mjs:60`: the "closed within 1 s" race becomes a read with a 10 s deadline (the negative control still fails without the fix, because the read never returns).
- The quarantine list that the implementation protocol asks of a repository ("load-sensitive tests in a named quarantine list with an owner who makes them robust; the list explains a red, it never skips the final run") starts as a section of `docs/development.md`. Each entry names the test, the observed failure and the owner. The first entry is `backend/tests/integration/test_bot_lock.py` (sub-second leases), owner: the repository owner. A listed test that fails in the final `yarn verify` is rerun alone on the same commit and on the base, and the result is written into the note; the final run is never skipped.

## 4. Implementation stages

Each substage is one commit that can be reverted alone, sized for one implementer's context. Order: S8.1 is independent; S8.2 → S8.3 → S8.4 → S8.5. Merge the umbrella tip before the first implementation commit and before review. Install this worktree's dependencies from the lockfiles first. One Docker build and one heavy run at a time; a run of more than a few minutes is announced with its expected time and load. Remove what is started: the acceptance projects' containers, volumes and locally built images, and the build cache they created.

## 5. Acceptance criteria

- **A1.** On a fresh clone with `.env` copied from `.env.example`, a non-default letters-and-digits `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` and the owner's test bot token added, `docker compose -p taskbot-e2e up --build -d --wait` exits 0 and ends with seven services `healthy` and `migrate` `exited (0)`; after a 2-minute window every container has `RestartCount` 0 and `OOMKilled` false; the shared `taskbot` containers keep their ids and start times.
- **A2.** Without a token, `docker compose -p taskbot-e2e up -d --wait` naming every service except `bot` ends with six services `healthy`; `docker compose run --rm seed <id> "<text>"` prints a link on the web port; that link's token reads the task through nginx (`GET /api/tasks` with the bearer).
- **A3.** Through nginx: `/`, `/index.html`, one hashed asset, a missing asset (404) and `GET /api/tasks` without a bearer (401 JSON from the API) each carry the five headers of 3.3 and no `Server` version; the asset carries the immutable cache header and is gzip-encoded when asked; a body above 64 KB to `/api/` is refused with 413. No host port other than `web`'s is published by the project.
- **A4.** With an SSE stream open through nginx, `docker compose restart api` ends the stream at the client, and a new ticket opens a new stream once the API is healthy, within the dashboard's 30 s back-off.
- **A5.** One task runs in each worker role's Linux child: the notify container logs `Voice recovery job completed` for the start-up sweep and again for a beat sweep at least 60 s later (`entrypoints/worker/notification.py:39`); a transcription job sent with `celery call` for a voice job id that does not exist makes the transcribe container log `Voice job missing: <id>` (`application/transcribe_voice.py:154`) and no failure line. Both containers stay `healthy` with `RestartCount` 0.
- **A6.** `docker compose stop bot` ends the bot with exit status 0 within its 40 s grace, and its log shows the polling stop and the producer close; an idle worker container stops with exit status 0 within seconds.
- **A7.** A second `docker compose up -d --wait` on the running stack leaves every long-running container's id and start time unchanged and runs `migrate` again to `exited (0)`; tasks survive `docker compose down` and `up` without `-v`.
- **A8.** The dump and restore commands of `docs/deployment.md`, with the non-default credentials of A1: after `down -v`, `up` and the restore, the same task rows are back.
- **A9.** With the `whisper` profile, starting from an empty `whisper-models` volume: the service becomes `healthy` after the download (time recorded); a download killed halfway leaves no `ggml-*.bin`, and the next start completes it; the fixture `backend/tests/fixtures/voice-en.ogg` posted to `/inference` from inside the network returns non-empty text on the read-only, non-root container (time recorded); a non-audio file returns the 500 body that S5 maps to `unsupported_audio` (W3).
- **A10.** For every container, `/proc/1/status` shows a non-zero uid, `docker inspect` shows `no-new-privileges`, no added capability beyond those the Compose file names with a reason, `ReadonlyRootfs` true unless exempted with a reason, `HostConfig.Memory` set and the `json-file` limits; the `whisper` container in the profile run included.
- **A11.** Every `FROM` (uv included) and every pulled `image:` names a patch-level tag and an index digest, and `docker buildx imagetools inspect` lists amd64 and arm64 for each (whisper: one per architecture stage).
- **A12.** During the acceptance run, PostgreSQL connections grouped by `client_addr` (mapped to container addresses) stay at or under the L3 budget per service and 25 in total; Redis clients are counted by `CLIENT LIST` and recorded.
- **A12'.** On the final commit, `docker compose config --hash postgres` and `--hash redis`, each run through `infra.mjs`'s command for project `taskbot`, are identical with no `.env`, with `.env` copied from the example, and with `POSTGRES_*` set in `.env` and in the shell.
- **A13.** The end-to-end test passes in `yarn verify`; the L4 tests wait on readiness signals or the shared budget; `yarn verify` passes on the final commit.
- **A14.** The README is at most about 200 lines; lines 1–40 name the three start steps and both voice switches; every command in it appears in the acceptance script's printed command list; `docs/development.md` and `docs/deployment.md` exist and the README links them.
- **A15.** The owner's live check (section 7, rows O1–O9) on the reviewed commit matches the accepted table, or the owner approves the difference.
- **A16.** `scripts/stack-acceptance.mjs` removes its project (`down -v --rmi local`) on success, on failure and on Ctrl-C; it picks free host ports at run time; it never prints `docker compose config` of the real `.env`.

## 6. Change profile

Delivery and configuration: new processes in containers, a new web server (nginx), a new optional external image (whisper.cpp), the shared development stack's definition, and one settings default. Touches: the public shape of the delivered stack (ports, variables, commands); authorization only through nginx headers and the unchanged bearer and ticket paths; concurrency only through stop and restart behaviour (grace periods, warm shutdown, the polling lock across restarts). No schema migration, no money, no change to the composition roots or the domain. Earns: the architecture-documentation check (S11 draws the result; `docs/deployment.md` states what the stack is), irreversibility for the shared stack (S8-D10: recreated once, volumes kept), and the census of real stored rows: none exists (the development database holds no user rows; there is no production), so the owner's rows are behaviours of the packaged stack (section 7).

## 8. Risks

- Linux prefork runs for the first time in the delivered stack; a child-init failure exits 0 and restarts under `unless-stopped`. A1's restart count, A5 and the end-to-end test of real workers are the checks; the logs name the cause.
- A bot with a missing or malformed token exits 2, and with a rejected token exits 1; both restart forever under `unless-stopped`. `docker compose ps` shows `Restarting`, and the README's troubleshooting line points at `docker compose logs bot`.
- One token polled from two places (a development bot and the Compose bot, or two Compose projects) gives alternating Telegram conflicts: their polling locks live in different Redis instances. The acceptance run and the owner's check stop any other poller first; the README says one bot per token and `docker compose down` after testing.
- The shared `postgres` and `redis` get memory limits; they serve every worktree's `yarn verify`, so the limits come from a full `yarn verify` peak, not from the light acceptance run.
- The end-to-end test opens 25 more PostgreSQL connections on the shared server while it runs (its bot, API and two workers); parallel `yarn verify` runs in several worktrees add up. R-ISO isolates databases, not connection slots.
- An OOM kill of a transcribe child leaves the acknowledgement at "Transcribing…" for one lease (450–460 s) per attempt; whisper killed mid-job gives a transient failure. A1 checks `OOMKilled`; `WHISPER_MEM_LIMIT` follows the chosen model.
- Digest pins age: security fixes need a deliberate update; `docs/deployment.md` names the procedure.
- A password changed in `.env` after the first start does not reach an existing volume, and `migrate` then fails while `postgres` is healthy; the README says `down -v` resets it and deletes the data.
- Until S8 integrates, a `yarn infra:up` from another checkout recreates the shared containers with the old definition (S8-D10).
- `docker compose up --wait` with a one-shot `migrate` has had version-dependent exit codes; A1 records it on Compose 5.1.4 and the README names the minimum version.
