## 1. Problem

The dashboard (S7) has no server to talk to. `create_app()` (`backend/src/taskbot/entrypoints/api/app.py`) serves only `GET /health`. S6 adds what the dashboard needs: a personal bearer token checked on every request, the user's task list and status changes, manual task deletion, one-time real-time tickets and the Server-Sent Events (SSE) stream of the user's task events. The OpenAPI document it exports is the single wire schema from which the dashboard's TypeScript types and Zod schemas are generated (umbrella section 4).

### 3.2 Settings and the composition root

`ApiSettings(BaseAppSettings, DatabaseSettingsMixin, RedisSettingsMixin)` in `infrastructure/settings/api.py` adds no variable: `.env.example` already lists `DATABASE_URL`, `REDIS_URL`, `REDIS_NAMESPACE` and `LOG_LEVEL`. `tests/unit/test_env_example.py` adds it to its tuple of models. `API_PORT` stays unread (the port is a uvicorn argument); S6 does not change that.

`create_app(services: ApiServices | None = None) -> FastAPI` registers every route and the error handlers. When `services` is given (tests, the replay script), `create_app` sets `app.state.services = services` at once and installs no lifespan work: `httpx.ASGITransport` does not run the lifespan, so services attached there would be missing in every ASGITransport test (executed, premise-library lens). When `services` is `None`, the lifespan runs `load_settings(ApiSettings)` and `open_api_services(settings)` and sets `app.state.services` for the application's life. Route dependencies read `request.app.state.services`. `export_schema`, `test_health` and the image's import check call `create_app()` with no environment, and the lifespan does not run for `openapi()` (executed, exploration B). A unit test calls a route over ASGITransport with fake services and no lifespan.

`open_api_services(settings)` is an async context manager over an `AsyncExitStack`, following the seed's root (`entrypoints/seed/__main__.py:32-36`): the SQL engine (`create_engine_and_sessions(str(settings.database_url))`, pool 5) is registered first and the Redis client (`create_redis_client(str(settings.redis_url), client_name="taskbot-api")`) second, so Redis closes first. `ApiServices` is a frozen dataclass of what the routes call: `AuthenticateToken(uows, Sha256TokenHasher())`, `ListTasks(uows)`, `ChangeTaskStatus(uows, SystemClock())`, `IssueRealtimeTicket(RedisTicketStore(client, SecretsTokenGenerator(), namespace))`, `ConsumeRealtimeTicket(store, uows)`, `StreamUserEvents(RedisEventSubscriber(client, namespace), uows, SystemClock())`, and the `EventPublisher` (`RedisEventPublisher(client, namespace)`) that routes pass to `publish_events` after a commit. S6.3 adds `delete_task: DeleteTask(uows)`.

`yarn dev:api` becomes `uvicorn --factory taskbot.entrypoints.api.app:create_app --reload --port 8000 --timeout-graceful-shutdown 2`. Without the timeout, uvicorn waits for every open SSE stream on Ctrl-C and on every reload (executed, exploration C). The image's command (`docker/backend.Dockerfile:24`) has no such flag; S6 does not edit Dockerfiles (umbrella section 5), so S8 adds it (Z10).

### 3.3 Authentication

One dependency, `current_user`, built on `HTTPBearer(auto_error=False)`: it reads the credentials and calls `AuthenticateToken.execute(token)`; a missing header, another scheme, an empty token, a token that fails `AuthenticateToken`'s pre-hash checks and an unknown token all raise `InvalidTokenError`. One exception handler maps `InvalidTokenError` and `InvalidTicketError` to `401` with `WWW-Authenticate: Bearer` and the body `{"detail": "Send /dashboard to the bot for a new link"}`, identical for every case (executed, exploration B; the cases are those of B5). `HTTPBearer` still gives the OpenAPI document its `securitySchemes` entry. Every route except `GET /health` and `GET /api/events` (which takes a ticket, 3.9) depends on `current_user`; a test walks the OpenAPI operations and expects the `401` on each protected one without a header. No CORS middleware: the browser reaches the API through one origin (umbrella D-08; the Vite proxy in development).

### 3.4 The task wire shape (S6-D1, S9 Y9)

`TaskView` (`domain/events.py`) gains `source_text: str` and length caps on the existing fields: `title: str = Field(max_length=TITLE_MAX)`, `description: str = Field(max_length=DESCRIPTION_MAX)` (4,096 once S9 integrates; 2,000 before). `source_text` has no cap: `MessageText` has none and the column has no check. A typed Telegram message is at most 4,096 characters; a transcript has no bound in this code (S9's design notes a looping transcript can exceed 4,096), and S5 owns transcripts (section 10). `TaskView.from_task(task, source_text)` takes the text as a second argument; entities still do not import wire models. Its callers outside production code are updated in S6.1: `tests/unit/test_use_cases.py:78`, `tests/unit/test_domain_entities.py:48`, and the direct `TaskView(...)` at `tests/integration/test_redis_adapters.py:35`.

Who builds a `TaskView`:

- `CreateTasksFromMessage.within` already holds the `MessageText`; it passes `text.value`. The bot (S4), the worker (S5) and the seed get the field without a change of their own.
- `ChangeTaskStatus` reads `uow.messages.get(task.inbound_message_id)` inside its unit of work, after the lock and before the `changed` branch, and returns it in `TaskChange`, which gains `view: TaskView`: the `200` of an unchanged status needs the text too. A missing message or (after S6.3) a `NULL` text raises `RuntimeError` as an invariant failure, like `change_task_status.py:31`: a task exists, so its message's text was not erased (3.7).
- The list reads it with a join (3.5); the row mapper raises the same invariant error on a `NULL` text.

The event models (`TaskCreated`, `TaskUpdated`, `AuthRevoked`, `TaskDeleted`) get `json_schema_serialization_defaults_required=True`, as `Health` has, so the generated TypeScript makes `type` required and narrows the union (executed, exploration C). `user_id` stays `Field(exclude=True)`; it is absent from the serialization schema and the generated code (executed, exploration A).

`TaskDeleted`: `type: Literal["task.deleted"]`, `user_id` (excluded), `task_id: int`. `DomainEvent` becomes the union of four. The Redis payload of every task event grows by the message text. Measured with `model_dump_json` (premise-code lens): about 300 bytes typical; 9.6 KB for owner row A8; 8.6 KB with a 120-character title, a 4,096-character description and a 4,096-character text in ASCII, about 17 KB in Cyrillic (two bytes per letter). A longer transcript makes it larger (section 10).

### 3.5 `GET /api/tasks` (S6-D2)

Query: `limit: int = Query(50, ge=1, le=200)`, `cursor: str | None = None`, `status: TaskStatus | None = None`. Response `TaskPage`: `items: list[TaskView]`, `next_cursor: str | None`.

Order: `inbound_message_id DESC, position ASC`, the order `list_for_user` uses today and the index `ix_tasks_user_message_position` serves. The cursor names the last item returned: `TaskCursor(inbound_message_id, position)`, written on the wire as `"<inbound_message_id>.<position>"` and documented as opaque. The route parses it with the pattern `^[0-9]{1,10}\.[0-9]{1,2}$` and then checks both numbers against int32 (`<= 2,147,483,647`); a malformed or out-of-range cursor (for example `9999999999.1`) is `422`. The page statement:

```sql
SELECT tasks.*, inbound_messages.text AS source_text
FROM tasks JOIN inbound_messages ON inbound_messages.id = tasks.inbound_message_id
WHERE tasks.user_id = :user_id
  [AND tasks.status = :status]
  [AND (tasks.inbound_message_id < :m OR (tasks.inbound_message_id = :m AND tasks.position > :p))]
ORDER BY tasks.inbound_message_id DESC, tasks.position ASC
LIMIT :fetch
```

The repository method is `TaskRepository.page_for_user(user_id, *, status, after, fetch) -> tuple[SourcedTask, ...]` and applies `fetch` as given; `SourcedTask(task: Task, source_text: str)` is a frozen domain dataclass in `domain/tasks.py`. `ListTasks.execute(user_id, *, status, after, limit) -> TaskListing` asks for `fetch = limit + 1` and trims: when `limit + 1` rows return, the listing holds the first `limit` and `next` names its last row; otherwise `next` is `None`. The domain result is `TaskListing(items: tuple[SourcedTask, ...], next: TaskCursor | None)`; the route maps it to the wire `TaskPage`.

A task created after the first page normally sorts before the cursor and never shifts or repeats a loaded one; a deleted task simply stops appearing. Identity values are allocated at insert and committed later, so a message that commits after a later-numbered one was paged past can appear on a later page and also arrive as `task.created`; the dashboard merges by task id (section 9 guidance; rare at assessment scale).

`list_for_user` is replaced by `page_for_user` in S6.1 and removed. Its callers move to `page_for_user(user_id, status=None, after=None, fetch=<large enough>)` or to the paged `ListTasks`: `application/list_tasks.py:11`; `tests/fakes/persistence.py:192`; `tests/contract/test_tasks.py:21,24,32`; `tests/unit/test_use_cases.py:237`; `tests/integration/test_persistence.py:188,201`; `tests/integration/test_seed.py:41,106,190`. The old `ListTasks.execute(user_id)` calls at `tests/unit/test_use_cases.py:60,74,75` and `tests/integration/test_persistence.py:245` take the new signature. S6.1 re-runs the grep at its base and records any other site.

### 3.6 `PATCH /api/tasks/{task_id}`

Path `task_id: int = Path(ge=1, le=2_147_483_647)`: `tasks.id` is int32, and a larger id would reach PostgreSQL as a cast error (`500`, executed). Body `TaskStatusChange {status: TaskStatus}` with `extra="forbid"`; an unknown status, `null`, `{}`, an extra field or invalid JSON is `422`. The route runs `ChangeTaskStatus.execute(user.user_id, task_id, status)`, maps `TaskNotFoundError` to `404` (another user's task and a missing one are indistinguishable), calls `publish_events(services.publisher, change.events)`, and returns `200` with `change.view`. The status values are `pending`, `in_progress` and `completed`. The same status returns `200` with the unchanged task and publishes nothing (`changed=False`, no event: `change_task_status.py:27-33`). Publication happens after the commit and before the response is sent; a failed publication is logged by `publish_events` and the response is still `200` (umbrella 3.4).

### 3.7 `DELETE /api/tasks/{task_id}` and erasing the text (S6-D5)

`DeleteTask.execute(user_id, task_id) -> tuple[DomainEvent, ...]`, in one unit of work:

1. `task = uow.tasks.get_for_update(user_id, task_id)`; `None` raises `TaskNotFoundError` (`404`).
2. `uow.tasks.delete(task.id)`.
3. `uow.messages.erase_text_if_unused(task.inbound_message_id)`: one statement, `UPDATE inbound_messages SET text = NULL WHERE id = :m AND NOT EXISTS (SELECT 1 FROM tasks WHERE inbound_message_id = :m)`.
4. `uow.record(TaskDeleted(user_id=user_id, task_id=task.id))`, commit.

The route (`status_code=204`, `response_class=Response`, so no body and no content type) publishes after the commit. A status change racing a deletion of the same task waits on the task lock and then gets `404`.

Since S9 (Y1) every path stores exactly one task per message, so step 3 erases the text on every deletion. The `NOT EXISTS` guard keeps the text while another task of the same message still shows it, which matters only for rows with several positions; no code path writes such rows after S9 and the census found none. Two concurrent deletions of the last two tasks of one such message could each still see the other's task under READ COMMITTED and leave the text in place; no lock is taken for this case that no path produces (section 10).

The message row stays. A late Telegram redelivery of the same message meets the unique key and creates nothing (`CreateTasksFromMessage.within` returns `DuplicateMessage`); the voice job keeps its `inbound_message_id`. `InboundMessage.text` becomes `str | None` and `InboundMessageRow.text` (`tables.py:88`) becomes `Mapped[str | None]`, so `alembic check` in `tests/integration/test_migrations.py:66-67` finds no drift; nothing reads `InboundMessage.text` today except the insert (grep at the base commit). Erasure is logical: PostgreSQL keeps the old tuple until vacuum, and `voice_jobs.file_id` still names the Telegram file.

Migration `0003_erasable_message_text`: `down_revision = "0002"`, `ALTER COLUMN text DROP NOT NULL`; downgrade sets `text = ''` where it is `NULL`, then restores `NOT NULL`. `tests/integration/test_migrations.py:155` expects head `0003`. It is written after S9 integrates (5). The README states that deleting a task erases the stored message text but not the message in the Telegram chat.

### 3.8 The stream rules (S6-D4)

**Port** (`domain/ports/messaging.py`):

```python
class EventSubscription(Protocol):
    async def next(self, timeout_seconds: float) -> str | None: ...

class EventSubscriber(Protocol):
    def subscribe(self, user_id: int) -> AbstractAsyncContextManager[EventSubscription]: ...
```

Entering the context returns only after the subscription is confirmed (S3 3.6). `EventStreamError` and `EventStreamGapError` move from `infrastructure/redis/subscription.py` to `domain/errors.py` (subclassing `DomainError`); the infrastructure module imports them with an explicit re-export (`from taskbot.domain.errors import EventStreamError as EventStreamError`), so S3's tests keep their imports unchanged (executed in a scratch copy: mypy strict, `lint-imports` and the 17 unit tests of `test_redis_adapters.py` pass; premise-code lens). The S3 design's STATUS line records "superseded in part by `docs/plans/2026-10-26-s6-api.md` (Z6)" in S6.1. `RedisEventSubscriber(client, namespace).subscribe(user_id)` returns `subscribe_user_events(client, namespace, user_id)`; `UserEventSubscription` already satisfies `EventSubscription`.

**`StreamUserEvents`** (`application/stream_events.py`), constructed with the subscriber, the unit-of-work factory and the clock; `RECHECK_SECONDS = 20` (umbrella's heartbeat interval, a code constant):

- `open(claims: TicketClaims) -> AbstractAsyncContextManager[UserEventStream]` subscribes for `claims.user_id`, then reads `users.get_token_version(claims.user_id)` once (the re-check S3 3.7 hands to S6, closing the window between consuming the ticket and the confirmed subscription). A different version or a missing user raises `InvalidTicketError` and leaves the subscription closed. Subscription errors propagate as `EventStreamError`.
- `UserEventStream.items() -> AsyncIterator[StreamItem]` yields, in order, `Connected()`, then events. It waits with `subscription.next(timeout)` where the timeout is the time left until the next re-check, and each re-check deadline is the previous re-check's start plus 20 s on the clock. A re-check therefore happens every 20 s even when events arrive more often (a re-check only on `None` would starve, exploration C); the adapter's idle PING after an expired deadline can add up to 2 s to one wait (S3 3.6).
  - An event is validated before it is forwarded: `EventEnvelope` (`type: Literal["task.created", "task.updated", "task.deleted", "auth.revoked"]`, extra fields allowed) parses the raw JSON; the raw string is forwarded unchanged as `Event(type, raw_json)`, because the published JSON cannot be validated back into the domain events (S3 exploration B 4.2). An invalid payload is logged and ends the stream.
  - `auth.revoked` is forwarded and then the stream ends.
  - A re-check that finds a different `token_version` or no user yields a synthesised `auth.revoked` (`AuthRevoked(user_id=…).model_dump_json()`) and ends: a dashboard cannot tell a missed revocation from a received one (Z5).
  - `EventStreamError` (including a gap) ends the stream. Any other `Exception` raised by the re-check's unit of work (the application layer cannot name SQLAlchemy's errors, and the domain has no persistence error type) ends it too; the `except Exception` carries a comment saying why. Both are logged once at warning level. The dashboard reconnects and refetches (umbrella D-08). `asyncio.CancelledError` is a `BaseException` and propagates.
  - The stream never raises after it started: an exception after the response headers ends the response as an `ExceptionGroup` without a clean close (executed, exploration B). This includes leaving the context: S3's `subscribe_user_events` raises `EventStreamError` when closing fails (`subscription.py:131-136`), and `open`'s exit catches and logs it, because the dependency's teardown runs after the response.

### 3.9 Tickets and `GET /api/events`

`POST /api/realtime/tickets` (bearer) → `IssueRealtimeTicket.execute(user)` → `201` with `RealtimeTicket {ticket: str, expires_in: int}`. The TTL becomes one domain constant, `TICKET_TTL_SECONDS = 30` in `domain/limits.py`; `RedisTicketStore`'s default and `expires_in` both read it. A Redis error while issuing or consuming a ticket is a `500` (no Redis type reaches the application layer); the dashboard's back-off retries it.

`GET /api/events?ticket=…` declares `ticket: str | None = None`, so a missing ticket is the uniform `401`, not FastAPI's `422`. The route's subscription dependency, a `yield` dependency, runs before FastAPI builds the response: it calls `ConsumeRealtimeTicket.execute(ticket)` (`401` on `InvalidTicketError`) and enters `StreamUserEvents.open(claims)` (`401` on the re-check, `503` with `Retry-After: 5` on `EventStreamError`). Only then does the route return; headers therefore go out after the subscription is confirmed (executed against real uvicorn, exploration A). The dependency's `finally` closes the subscription; it runs on a client abort at every moment tested (idle after headers, before the first item, during a slow subscribe; executed). A failure while closing is logged, not raised (3.8). `EventSource` does not expose the `: connected` comment; the dashboard treats `onopen` as the confirmed subscription.

The route uses `response_class=EventSourceResponse` (`fastapi.sse`), which sets `Cache-Control: no-cache` and `X-Accel-Buffering: no`. Its generator maps `Connected` to `ServerSentEvent(comment="connected")` and `Event` to `ServerSentEvent(raw_data=raw_json)` with no `event:` field, so the dashboard reads every event through `onmessage` and parses the envelope with the generated discriminated-union schema. FastAPI adds its own `: ping` comment every 15 s on an idle stream; that is the wire keep-alive, below nginx's read timeout (S8) and the dashboard's own timers. The 20 s rule is the `token_version` re-check (Z4).

For the generated schema, the route declares `responses={200: {"model": ServerEvent}}`, where `ServerEvent` is `RootModel[Annotated[TaskCreated | TaskUpdated | TaskDeleted | AuthRevoked, Field(discriminator="type")]]` in `entrypoints/api/realtime.py`. The union is written inline, not through the `DomainEvent` `type` alias: with the alias FastAPI emits a separate `DomainEvent` component and `zServerEvent` becomes an alias of it (executed, premise-library lens). FastAPI then writes `schema: {$ref: ServerEvent}` beside its native `itemSchema`, and `@hey-api/openapi-ts` 0.99 generates `zServerEvent` as a `z.discriminatedUnion("type", …)` and the `ServerEvent` type (executed, exploration A; with `itemSchema` alone it generates `unknown`).

### 3.10 Error mapping

| Condition | Status | Body |
|---|---|---|
| no, malformed or unknown bearer token; missing, unknown, used, expired or stale ticket | 401, `WWW-Authenticate: Bearer` | `{"detail": "Send /dashboard to the bot for a new link"}` |
| task of another user or missing (PATCH, DELETE) | 404 | `{"detail": "Task not found"}` |
| invalid body, path, `limit`, `status` or `cursor` | 422 | FastAPI's validation body |
| Redis subscription unavailable when the stream opens | 503, `Retry-After: 5` | `{"detail": "Real-time events are unavailable"}` |
| unexpected exception | 500 | FastAPI's default; logged |

The uvicorn access log prints the ticket in the query string. A ticket is single-use and lives 30 s, so the log shows only spent or expiring tickets; S6 keeps the access log (recorded in the README).

## 4. Approaches considered

1. **Minimal**: the stream loop in the route, tested only through a real server and Redis; S3's code untouched. Lost: the authorization rules of the stream would live in an entry point and have no fast test.
2. **Clean** (chosen, S6-D4): the port and `StreamUserEvents` of 3.8; the rules are unit-tested with a fake subscription and a fake clock; costs one new file (`application/stream_events.py`), a port added to an existing module and two error classes moved from S3.
3. **Local interface**: the loop in the route over a Protocol declared in `entrypoints`; unit-testable, but a port outside `domain`, against the repository guide.

Within approach 2, the alternative for the stream response was a `StreamingResponse` subclass with manual SSE framing and a `try/finally` around `__call__`; it lost because the `yield` dependency gives the same cleanup on every abort tested and keeps FastAPI's SSE headers and keep-alive.

REST tests use ASGITransport with `create_app(services=...)`.

- **B1 Wire shape.** `TaskView` of a task built by `CreateTasksFromMessage` and by `ChangeTaskStatus` (changed and unchanged status) carries the message text; the published `task.created` and `task.updated` JSON has the keys `id, inbound_message_id, position, title, description, status, created_at, updated_at, source_text` and no `user_id`; a 121-character title or a description over `DESCRIPTION_MAX` fails `TaskView` validation.

Guidance for S7 that follows from this design, not a departure:

- On `auth.revoked` or a closed stream the dashboard reconnects; the `401` on the ticket request is what signs it out. Clearing the token on `auth.revoked` alone would erase a newer token that another tab already stored.
- Tasks are merged by id. A `task.created` or `task.updated` for an unloaded task is inserted when it sorts inside the loaded range of the list or column it belongs to (by `inbound_message_id DESC, position ASC`), and ignored otherwise; a later page then brings it.
- An update is applied only when its `updated_at` is later than the stored one (S2 guarantees a strictly increasing `updated_at` per real change), so two `PATCH`es published in the wrong order cannot leave the older status.
- Deleted ids are remembered for the page's life; a later event or page row for such an id is dropped, and a `404` on `PATCH` or `DELETE` removes the card.

## 10. Verification and risks

Transitive importers of the changed modules (`domain/events.py`, `domain/messages.py`, `domain/ports/*`, `application/create_tasks.py`, `change_task_status.py`, `list_tasks.py`, `infrastructure/redis/subscription.py`, `infrastructure/sqlalchemy/*`) run on base and head with outputs compared: the whole backend unit suite, the contract suite on both parameters, `tests/integration/test_redis_adapters.py`, `test_redis_subscription_cancellation.py`, `test_seed.py`, `test_persistence.py`, `test_migrations.py`, and the S2, S3 (and S9 after the merge) replay scripts.

Risks carried:

- **S9 merge.** S9 changes `create_tasks.py` next to the line S6.1 changes (one mechanical conflict, executed in a scratch clone), adds migration `0002`, and edits `README.md` and `backend/AGENTS.md`. The merge rule of section 5 applies.
- **Unbounded `source_text`.** `MessageText` and the column have no length limit; a long transcript makes every event and page row of that task larger. Typed messages are at most 4,096 characters. A cap belongs to whoever bounds transcripts (S5); recorded for the lead.
- **Payload growth.** About 17 KB per event at S9's caps in Cyrillic; Redis pub/sub output buffers allow 8 MB over 60 s per subscriber. Acceptable at assessment scale.
- **Open-stream resources.** Each stream holds one Redis connection and nothing caps streams per user or per process; one token holder could open thousands and press Redis `maxclients` (10,000), which the broker shares (adversarial lens, MED, not executed). Not built: a per-user cap is out of proportion for a single-user assessment; the README names the limit.
- **Multi-position messages.** The text-erasure guard is not serialised for two concurrent deletions of the last two tasks of one message (3.7); no code path writes such messages after S9.
- **Out-of-order identity commits** can show a task on a later page and as `task.created`; S7 merges by id (3.5).
- **FastAPI's ping interval** is a private module global (`fastapi.routing._PING_INTERVAL`); tests may patch it, production does not depend on its value beyond being under the proxy timeout.
- **Access log** carries spent tickets (3.10).
- **S9's `0002` downgrade** fails once a description over 2,000 characters exists; `0003`'s downgrade is independent of it. Recorded for S9 and the lead.
